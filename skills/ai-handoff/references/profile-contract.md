# Profile and variant contract

Profile fields: provider, supported surfaces, context placement, durable-instruction conventions, execute/check/fallback recipe, official sources, checked date and limitations. Profiles describe documented conventions, not actual access. Unknown provider uses generic without invented commands, costs, model limits or ranking.

## Retain across variants
Objective/user task, scope/exclusions, stack/conventions, visual rules, pinned patterns/versions, local edits, output contract and acceptance criteria/required flags. Adapt only delivery, wording and capability-dependent actions. Requirements for real persistence/data stay explicit. Produce a comparison of retained constraints for multi-provider exports.

## Transfer context
Identify root/attachments and which source references recipient must receive. Producer access_status read is historical provenance, not a claim recipient read it; receiving AI must read/verify sources again. Map inaccessible paths to provided attachments or inline sections and record missing material. Never put secrets into a packet. Keep project-specific data out of reusable shared profiles.

## Durable guidance
Use repo instructions already present. Only edit/bootstrap instruction files when the user requests it; propose short scoped snippets otherwise. Do not override global settings or erase existing guidance. Source official docs for new commands, check installed-version applicability, and use host help/manual fallback if uncertain.

## Outcome evidence
Packet generated means export prepared, not design/code executed. The receiving environment records its own changes/checks. User-provided logs are labeled user_provided, not checks executed by the producing plugin. Provider docs checked is separate from provider execution tested.
