# Project Brief

Turn intent into a usable design brief without inventing research.

1. Read [context contract](../design-studio/references/context-contract.md). Reuse a brief that already answers the task.
2. Capture the user's outcome and primary user task before proposing features. Ask one focused consequential question at a time; proceed with labeled low-impact assumptions.
3. Use [brief template](templates/project-brief.md) to record purpose, audience, evidence, scope, screens, constraints, success metric/target, stack, design direction, source locations and open decisions. Unprovided targets stay unknown rather than fabricated.
4. Use [preferences template](templates/preferences.md) only for preferences actually stated. Project rules may override personal visual preferences; preserve existing repo technology.
5. Reflect the brief so the user can correct it. Confirm consequential uncertain choices, not routine steps already requested. Feed the brief into UX/UI work and record updates when intent changes.

Example: salon booking app → outcome “fewer missed appointments”; metric no-show rate; baseline/target unknown; research hypotheses about reminders labeled unverified; proposed flow includes rescheduling rather than adding speculative loyalty features.

Common mistakes: invented interviews/personas, features before purpose, success metrics without targets marked unknown, storing preferences inside packaged skills, and recreating a brief for every screen.
